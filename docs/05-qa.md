# 書き出し・検品

## MRQ→MP4

既存Movie Render Queue plugin、Level Sequence、camera cutsを確認して新projectだけに設定。最初に540×960等の小preview。warm-up値はsceneで調整し、初フレーム黒・shader未完を実画像で検出。ログのmap load成功だけで合格にしない。

推奨開始preset（実装済みassetではない）：vertical=1080×1920、30fps、8秒=240frame。landscape=1920×1080、30fps、10秒=300frame。frame範囲は終端排他とし重複frameを作らない。色空間/露出/warm-up/AA/seed/音の有無を記録。MRQ画像列→既存ffmpegでH264/yuv420p、必要音はAAC/48kHzへ。既存encoderがなければ勝手に導入しない。

## エンコード前の画像列検査

MRQの終了通知・exit 0・MP4のframe数は、いずれも元画像列そのものの正しさを証明しない。通知が成功していても、画像列に欠番や余分なframeが混じれば、その後のencodeは静かに別の映像になる。MP4側の240frame確認だけでは「元画像列に241枚ある」ことを排除できない。

そこでencodeの前に、期待範囲と実際の画像列を照合する。`scripts/Measure-UERenderArtifacts.ps1`は読み取り専用のhelperで、対象dirを改名・修復・削除しない。

```powershell
.\scripts\Measure-UERenderArtifacts.ps1 `
  -FramesDirectory '<project>\Out\run_<runid>\frames' `
  -StartNumber 0 `
  -EndNumberExclusive 240 `
  -FrameStep 1 `
  -FrameNumberOffset 0 `
  -ExpectedWidth 1080 `
  -ExpectedHeight 1920 `
  -RunId '<runid>' `
  -SourceRevision '<template commit>' `
  -ReportPath '<project>\Out\run_<runid>\evidence\frames-check.json'
```

`-FrameStep` / `-FrameNumberOffset` は MRQの `Output Frame Step` / `Frame Number Offset` の実値を書き写す。既定（1と0）は従来の連番と同じ。

- 期待枚数だけでなく、全対象ファイルの番号集合を照合する。先頭・中間・末尾の欠番、範囲外の余分なframe、桁数/拡張子の揺れ、想定外の名前、0 byte、decode不能、解像度不一致を検出する。
- 入力は明示する。`-StartNumber`は0以外も指定できるが、render範囲から書き写す。`-EndNumberExclusive`は終端排他。解像度を省くと解像度判定は`unverified`になり、passにならない。
- **MRQの`Output Frame Step`を使ったrenderは、連番ではなく格子で出力される。** `-FrameStep`と`-FrameNumberOffset`（既定は1と0＝従来の連番）で、期待するindexの格子を宣言する。step=2・240frame範囲なら期待indexは`0,2,4,…,238`の120枚で、`-FrameStep 2 -EndNumberExclusive 240`がpassする。宣言しないと、helperは格子の不一致を`index_lattice_mismatch`として報告する（実ファイルが公差2の等差数列で、宣言stepが1のとき）。この場合の欠番は「画像列の欠落」ではなく「宣言格子の食い違い」であり、`missing_frames`を主因にしない。**MRQの`Output Frame Step` / `Frame Number Offset`はQAへ実値を記録し、同じ値をhelperへ渡す。** 推測でstepを決めない。
- **`Handle Frame Count`は宣言rangeの外へ連続frameを足す。** 連続なので`index_lattice_mismatch`ではなく`out_of_range_frames`になる。handle込みが納品対象なら宣言rangeを広げる。どちらを納品したかをQAに書く。
- decodeは既存環境の`ffprobe`を使うだけ。PATHに無い場合は`-DecoderPath`で既存実体を明示する。decoderが無い・失敗・timeoutのときはdecode=`unverified`または`fail`であり、総合passにしない。timeoutは既定10秒で、その場合も成功へ丸めない。
- reportは新規の明示出力先だけに書き、既存fileを上書きしない。文字列上の内部pathに加え、`FramesDirectory`またはreport親pathの既存componentにjunction/symlink等のreparse pointがある場合は、実効境界を安全に照合できないため入力検査・親dir作成より前に拒否する。reportを画像列dirの外側にある通常のdirectoryへ書く。helper自身は入力のhashを計算しない（読み取りしかしない）。「入力が変わっていない」ことは回帰suite `scripts/Test-UERenderArtifacts.ps1` が検証する：suiteが作った21のfixtureディレクトリすべてについて、構築直後の全file名・SHA256をbaselineとして記録し、末尾で再比較して**追加・削除・内容変更をpathで名乗り上げる**。また`reports/`は件数と非空を別途照合し、`Production/`配下の無視される残骸も直接列挙する（`git status --untracked-files=all`は`.gitignore`の`Production/*`を見ないため、これだけでは不十分）。このgate自体が空assertに戻らないよう、「fixtureを壊せばsuiteはそのpathを名指しで落ちる」ことをsuite内の負例groupで固定する。
- 終了codeはpass=0、fail=1、unverified=2。

判定は次の5つを独立に扱い、1つの欄でまとめない。

| 判定 | 何を見るか | 何を証明しないか |
|---|---|---|
| render通知/exit | MRQの終了通知・exit code | 画像列の完全性 |
| 画像列 | 番号集合・格子（step/offset）・命名・サイズ・decode・解像度 | render成功・映像の見た目 |
| MP4 | 既存ffprobeで幅/高さ/fps/frame数/秒数/codec/音声 | 先頭/中間/末尾の見た目 |
| 目視・全編再生 | 0付近/中間/末尾、全編、loop継ぎ目 | 音の内容 |
| 音 | 実聴取。stream存在は聴取ではない | 映像の見た目 |

画像列のfailは、**成果物の不備**（欠番・余分・0 byte・decode不能・解像度不一致）と**宣言格子の不一致**（`index_lattice_mismatch`）を区別して読む。後者は画像列が壊れているのではなく、helperへ渡したstep/offsetがMRQの実値と違う。原因を切り分ける前にencodeへ進まない。

画像列がpassでも、render成功・全編目視・音・loop品質は別項目のまま`unverified`とする。逆に通知成功/exit 0の記録があっても、画像列の負例をpassへ読み替えない。

旧runの同数frameが混入していないことは、この検査だけでは判定できない。run専用の新規出力先と所有権照合を前提にする。

以下は命名規則を合わせてから使う例で、実行済みscriptではない。`frames/%06d.png`は000000.png開始、`Out/final`は当該run内に読み替える。

**連番の画像列（step=1）:**

```text
ffmpeg -n -framerate 30 -start_number 0 -i frames/%06d.png -frames:v 240 -c:v libx264 -pix_fmt yuv420p -crf 18 -movflags +faststart Out/final/clean.mp4
ffprobe -v error -count_frames -show_entries stream=index,codec_type,codec_name,width,height,r_frame_rate,nb_read_frames,sample_rate,channels -show_entries format=duration,size -of json Out/final/clean.mp4
```

**格子の画像列（step=2）:** image2の`%06d`連番templateは**最初の欠番で入力を終える**。`-i`の`%06d`に格子をそのまま渡すと、ffmpegは**exit 0で1frameのMP4**を作る（stderrにerrorは出ない）。実測（本host、ffmpeg 8.1.2、120枚のstep-2格子）では`FFMPEG_EXIT=0`・`nb_read_frames=1`・`duration=0.033333`。尺が1frameでも成功終了するので、ffprobeのframe数を必ず見る。

格子をencodeするときは、**当該runの新しい出力先**へ連番に振り直した複製を作り、そこを`-i`に渡す（検査対象の画像列は改名しない）。

```text
# 1) 格子を連番へ振り直す（元の画像列は変更しない）
$i = 0; Get-ChildItem '<frames>' -Filter *.png | Sort-Object Name | ForEach-Object { Copy-Item $_.FullName (Join-Path '<renumbered>' ('{0:D6}.png' -f $i)); $i++ }

# 2) 振り直した連番をencode。frame数は step 倍率で減るので -frames:v は格子の枚数に合わせる
ffmpeg -n -framerate 30 -start_number 0 -i '<renumbered>/%06d.png' -frames:v 120 -c:v libx264 -pix_fmt yuv420p -crf 18 -movflags +faststart Out/final/step2.mp4
ffprobe -v error -count_frames -show_entries stream=nb_read_frames,r_frame_rate -show_entries format=duration -of json Out/final/step2.mp4
```

実測（本host、ffmpeg 8.1.2、120枚）：振り直し後は`FFMPEG_EXIT=0`・`nb_read_frames=120`・`duration=4.000000`（`-framerate 30`）。同じ格子を`-framerate 15`で読むと`nb_read_frames=120`・`duration=8.000000`。**stepで間引いたrenderは実時間より短く出るので、どちらの尺を納品したかをQAに書く。** 等倍で見たいなら`-framerate`を元fpsの1/stepにし、尺をffprobeで確認する。この`-frames:v`は出力上限であり、元画像列の整合性はhelperの判定で担保する（DOT-3217のlandscape切り落としとは別項目）。

`-pattern_type glob`はWindowsの一部buildで未対応（本hostのffmpeg 8.1.2は`globbing is not supported by this libavformat build`でexit -40）。`concat`demuxerは1枚1frameの`-r`を明示しないと3〜4frameで止まる（同buildで実測）。**どちらも格子のencode手段として使わない。**

音あり版は同期・尺を合わせ、採用音の権利を確認。音声streamの存在は聴取確認ではない。
公式MRQ： https://dev.epicgames.com/documentation/en-us/unreal-engine/movie-render-pipeline-in-unreal-engine

## 視覚・ループ・音

- エンコード前の画像列検査結果（`evidence/frames-check.json`）を、MP4のffprobe結果と並べて記録する。両方passでも目視の代わりにしない。
- ffprobe出力を保存し、実解像度/codec/fps/frame数/秒数/音声を期待値と照合。拡張子や非空サイズだけで合格にしない。
- 0付近/中間/末尾のフレーム、thumbnailを目視。真っ黒、露出白飛び、被写体切れ、破綻、素材欠落を確認。
- 全編を再生。末尾→先頭を2回連結した再生でも動き/光/カメラ/粒子/音の継ぎ目を確認。数枚目視だけで全編・継ぎ目合格にしない。
- 黒frameが意図外ならwarm-up/camera cut/開始tick/streaming/exposureを調査し再render。黒スクショを「検品済み」としない。
- 実際のゲームと動画の音を聴く。音量、loop click、clip、意図外の無音を確認。遠隔hostで聴けないなら聴取Unverified、owner用previewを渡す。

## Play / 展開版チェック

- 起動map・Pawn・開始姿勢。座位/立位が仕様なら両方。
- mouse視点、移動、zoomの往復、台や壁のcollision、外周の落下/抜け、Rリセット、H help、Esc/終了。未実装の機能は合格にせず仕様上の非対象と区別。
- 最新版で5分以上の連続鑑賞。測定時間・操作/無操作の内訳、hardware、解像度、品質、frame time平均/スパイク/観測方法を記録。
- FPS目安は案件ごとに合意。初期提案は最低30fps（33.3ms）、目標60fps（16.7ms）。これは測定実績でも共通保証でもない。
- 過去Bonfire play8は720p平均13.7〜14.8ms、144.5ms hitchを1回報告。別host/別版へ転用しない。
- Shipping ZIP別展開→起動・操作を再確認。Editor PlayだけではShippingの入力/終了を証明しない。

QA記録は合否・版/hash・実施者・日時・証拠・未確認をセットにする。
