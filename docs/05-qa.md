# 書き出し・検品

## MRQ→MP4

既存Movie Render Queue plugin、Level Sequence、camera cutsを確認して新projectだけに設定。最初に540×960等の小preview。warm-up値はsceneで調整し、初フレーム黒・shader未完を実画像で検出。ログのmap load成功だけで合格にしない。

推奨開始preset（実装済みassetではない）：vertical=1080×1920、30fps、8秒=240frame。landscape=1920×1080、30fps、10秒=300frame。frame範囲は終端排他とし重複frameを作らない。色空間/露出/warm-up/AA/seed/音の有無を記録。MRQ画像列→既存ffmpegでH264/yuv420p、必要音はAAC/48kHzへ。既存encoderがなければ勝手に導入しない。

## エンコード前の画像列検査

MRQの終了通知・exit 0・MP4のframe数は、いずれも元画像列そのものの正しさを証明しない。通知が成功していても、画像列に欠番や余分なframeが混じれば、その後のencodeは静かに別の映像になる。MP4側の240frame確認だけでは「元画像列に241枚ある」ことを排除できない。

そこでencodeの前に、期待範囲と実際の画像列を照合する。`scripts/Measure-UERenderArtifacts.ps1`は読み取り専用のhelperで、対象dirを改名・修復・削除しない。

```powershell
.\scripts\Measure-UERenderArtifacts.ps1 `
  -FramesDirectory '<project>\Out\run_<runid>\frames' `
  -StartNumber 0 `
  -EndNumberExclusive 240 `
  -ExpectedWidth 1080 `
  -ExpectedHeight 1920 `
  -RunId '<runid>' `
  -SourceRevision '<template commit>' `
  -ReportPath '<project>\Out\run_<runid>\evidence\frames-check.json'
```

- 期待枚数だけでなく、全対象ファイルの番号集合を照合する。先頭・中間・末尾の欠番、範囲外の余分なframe、桁数/拡張子の揺れ、想定外の名前、0 byte、decode不能、解像度不一致を検出する。
- 入力は明示する。`-StartNumber`は0以外も指定できるが、render範囲から書き写す。`-EndNumberExclusive`は終端排他。解像度を省くと解像度判定は`unverified`になり、passにならない。
- decodeは既存環境の`ffprobe`を使うだけ。PATHに無い場合は`-DecoderPath`で既存実体を明示する。decoderが無い・失敗・timeoutのときはdecode=`unverified`または`fail`であり、総合passにしない。timeoutは既定10秒で、その場合も成功へ丸めない。
- reportは新規の明示出力先だけに書き、既存fileを上書きしない。文字列上の内部pathに加え、`FramesDirectory`またはreport親pathの既存componentにjunction/symlink等のreparse pointがある場合は、実効境界を安全に照合できないため入力検査・親dir作成より前に拒否する。reportを画像列dirの外側にある通常のdirectoryへ書く。helper自身は入力のhashを計算しない（読み取りしかしない）。「入力が変わっていない」ことは回帰suite `scripts/Test-UERenderArtifacts.ps1` が検証する：suiteが作った17のfixtureディレクトリすべてについて、構築直後の全file名・SHA256をbaselineとして記録し、末尾で再比較して**追加・削除・内容変更をpathで名乗り上げる**。また`reports/`は件数と非空を別途照合し、`Production/`配下の無視される残骸も直接列挙する（`git status --untracked-files=all`は`.gitignore`の`Production/*`を見ないため、これだけでは不十分）。このgate自体が空assertに戻らないよう、「fixtureを壊せばsuiteはそのpathを名指しで落ちる」ことをsuite内の負例groupで固定する。
- 終了codeはpass=0、fail=1、unverified=2。

## CIのdecoder固定

CIの`render-artifacts` jobは、runner imageに入っている`ffprobe`をそのまま使わない。`scripts/ffprobe-pin.json`に配布元URL・archiveのSHA-256・`ffprobe.exe`のSHA-256・期待するversion行のprefixを記録し、`scripts/Install-PinnedFfprobe.ps1`がその3点を照合してから検査に使う。以前はPATHに`ffprobe`があれば任意版を受け入れ、無い場合はversion指定なしの`choco install ffmpeg`に落ちていたため、同じcommitでもrunner imageやpackage更新でdecode判定が変わり得た。

- 固定した実体はcheckoutの外（`$env:RUNNER_TEMP`、ローカルでは`%TEMP%\ffprobe-pin`）に置き、template・`Production/`・成果物へ同梱しない。CI内のfixture decodeにのみ使う。
- 取得元は`GyanD/codexffmpeg` 8.1.2 essentials build（GPL-3.0-or-later）。archiveのsha256は`db580001…`、`ffprobe.exe`は`b49ccc7c…`、versionは`ffprobe version 8.1.2-`で始まる行。ライセンスはCI内利用に閉じ、repoの配布条件（`LICENSE-NOTICE.md`）とは別物として扱う。
- `scripts/Test-FfprobePin.ps1`が負例を固定する：manifestの項目欠落・archiveの1 byte改変・PATHの手前に別の`ffprobe`がある場合をすべて拒否し、固定版のbytesとversionだけを受け入れる。suiteはcheckout内に何も書かない。
- 判定ロジック（`Measure-UERenderArtifacts.ps1`のdecode/timeout優先順位）と既存assertionは変えていない。固定したのはdecoderの実体だけ。
- 版を上げる場合は`ffprobe-pin.json`の3つの値（archive sha256・binary sha256・version prefix）を同時に更新し、`Test-FfprobePin.ps1`と`Test-UERenderArtifacts.ps1`を通す。片方だけ更新したmanifestはinstallerが拒否する。

判定は次の5つを独立に扱い、1つの欄でまとめない。

| 判定 | 何を見るか | 何を証明しないか |
|---|---|---|
| render通知/exit | MRQの終了通知・exit code | 画像列の完全性 |
| 画像列 | 番号集合・命名・サイズ・decode・解像度 | render成功・映像の見た目 |
| MP4 | 既存ffprobeで幅/高さ/fps/frame数/秒数/codec/音声 | 先頭/中間/末尾の見た目 |
| 目視・全編再生 | 0付近/中間/末尾、全編、loop継ぎ目 | 音の内容 |
| 音 | 実聴取。stream存在は聴取ではない | 映像の見た目 |

画像列がpassでも、render成功・全編目視・音・loop品質は別項目のまま`unverified`とする。逆に通知成功/exit 0の記録があっても、画像列の負例をpassへ読み替えない。

旧runの同数frameが混入していないことは、この検査だけでは判定できない。run専用の新規出力先と所有権照合を前提にする。

以下は命名規則を合わせてから使う例で、実行済みscriptではない。`frames/%06d.png`は000000.png開始、`Out/final`は当該run内に読み替える。

```text
ffmpeg -n -framerate 30 -start_number 0 -i frames/%06d.png -frames:v 240 -c:v libx264 -pix_fmt yuv420p -crf 18 -movflags +faststart Out/final/clean.mp4
ffprobe -v error -count_frames -show_entries stream=index,codec_type,codec_name,width,height,r_frame_rate,nb_read_frames,sample_rate,channels -show_entries format=duration,size -of json Out/final/clean.mp4
```

音あり版は同期・尺を合わせ、採用音の権利を確認。音声streamの存在は聴取確認ではない。
公式MRQ： https://dev.epicgames.com/documentation/en-us/unreal-engine/movie-render-pipeline-in-unreal-engine

## 視覚・ループ・音

- エンコード前の画像列検査結果（`evidence/frames-check.json`）を、MP4のffprobe結果と並べて記録する。両方passでも目視の代わりにしない。
- ffprobe出力を保存し、実解像度/codec/fps/frame数/秒数/音声を期待値と照合。拡張子や非空サイズだけで合格にしない。
- 0付近/中間/末尾のフレーム、thumbnailを目視。真っ黒、露出白飛び、被写体切れ、破綻、素材欠落を確認。
- 全編を再生。末尾→先頭を2回連結した再生でも動き/光/カメラ/粒子/音の継ぎ目を確認。数枚目視だけで全編・継ぎ目合格にしない。
- 黒frameが意図外ならwarm-up/camera cut/開始tick/streaming/exposureを調査し再render。黒スクショを「検品済み」としない。
- 実際のゲームと動画の音を聴く。音量、loop click、clip、意図外の無音を確認。遠隔hostで聴けないなら聴取Unverified、owner用previewを渡す。

## Play / 展開版チェック

- 起動map・Pawn・開始姿勢。座位/立位が仕様なら両方。
- mouse視点、移動、zoomの往復、台や壁のcollision、外周の落下/抜け、Rリセット、H help、Esc/終了。未実装の機能は合格にせず仕様上の非対象と区別。
- 最新版で5分以上の連続鑑賞。測定時間・操作/無操作の内訳、hardware、解像度、品質、frame time平均/スパイク/観測方法を記録。
- FPS目安は案件ごとに合意。初期提案は最低30fps（33.3ms）、目標60fps（16.7ms）。これは測定実績でも共通保証でもない。
- 過去Bonfire play8は720p平均13.7〜14.8ms、144.5ms hitchを1回報告。別host/別版へ転用しない。
- Shipping ZIP別展開→起動・操作を再確認。Editor PlayだけではShippingの入力/終了を証明しない。

QA記録は合否・版/hash・実施者・日時・証拠・未確認をセットにする。
