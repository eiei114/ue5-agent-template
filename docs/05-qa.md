# 書き出し・検品

> 生成物へ同梱された写しとして読むとき: この文書が案内する `scripts/`・`templates/` とほかの `docs/` は source checkout（ue5-agent-template のrepo root）相対で、生成物には同梱されない。`template-lock.json` の `template_repository` / `template_commit` で source checkout を特定し、そのrootを作業directoryにしてコマンドを実行する。同梱の規則は `docs/07-architecture.md`（参照閉包契約）。

## MRQ→MP4

既存Movie Render Queue plugin、Level Sequence、camera cutsを確認して新projectだけに設定。最初に540×960等の小preview。warm-up値はsceneで調整し、初フレーム黒・shader未完を実画像で検出。ログのmap load成功だけで合格にしない。

推奨開始preset（実装済みassetではない）：verticalとlandscape（数値は`templates/CAPTURE-PRESETS.json`からのみ導出）。frame範囲は終端排他とし重複frameを作らない（機械的な検出は画像列検査の`checks.frame_variety`。既定は`unverified`で、呼び出し側が宣言したときだけpass/failになる。「同一frameの検出」節）。色空間/露出/warm-up/AA/seed/音の有無を記録。書き出し経路は2つあり、どちらを使ったかを記録する（次節）。経路AはMRQ画像列→既存ffmpegでH264/yuv420p（宣言を満たしたとみなす条件は「エンコードとMP4の尺検査」節のpixel format照合規則だけ）、必要音はAAC/48kHzへ。経路BはMRQの出力設定`H.264 MP4 [8bit]`で直接MP4。UE同梱のMRQ出力設定もencoderとして数える。外部ffmpegの新規導入はしない（無いhostでは経路Bで書くか、既存encoderのあるhostへ回す）。

## 書き出し経路（2つ）

MP4に至る経路は2つある。片方だけを書かない。どちらを使ったかを`templates/QA.md`の`encode_path`へ記録する。既定は経路Aで、経路Bは既定にしない。

| 経路 | 手順 | 元の画像列 | 検査との関係 |
|---|---|---|---|
| A: `mrq-image-sequence+external-ffmpeg` | MRQのimage sequence出力（`.png`/`.exr`）→ 既存`ffmpeg`でH.264/yuv420p | 存在する | 「エンコード前の画像列検査」がそのまま効く（`.exr`列なら`-Extension .exr`を渡す） |
| B: `mrq-native-mp4` | MRQの出力設定`H.264 MP4 [8bit]`（`UMoviePipelineMP4EncoderOutput`）で直接MP4 | **存在しない** | 画像列の検査対象が無い。MP4のffprobeと目視で判定する |

- 経路BのencoderはUEが同梱する`MovieRenderPipelineMP4Encoder`モジュール（`MovieRenderPipeline.uplugin`、`PlatformAllowList`はMac/Win64/Linux）で、recipeの`required_plugins`（`MovieRenderPipeline`）を有効にしたprojectに既に含まれる。追加install・追加課金は不要。
- ただしUE 5.8.4の同梱sourceは`Source/MovieRenderPipelineMP4Encoder/Private/Windows/MoviePipelineMP4Encoder.h:11`で`Experimental.`と明記している。したがって経路Bを既定にしない（画質・音声同期・安定性はこのrepoでは未検証）。
- 経路Bのときは、出力設定の表示名（`H.264 MP4 [8bit]`）を`mrq_output_setting`へ、`source_png_sequence`を「存在しない」と書く。**「元PNG列が無いから unverified」ではなく「経路Bとして記録済み」とする。**片方の経路の前提を他方へ流用しない。
- 経路Aの`ffmpeg`コマンド（`%06d`連番・`-frames:v`）を、経路BのMP4へ流用しない。経路BのMP4は`ffmpeg -n`の再encodeも画像列検査も通らないため、判定はffprobeと目視で行う。**音が対象なら実聴取も必須**で、音声streamの存在やffprobeの音声欄は聴取の代わりにしない（「視覚・ループ・音」節と同じ）。この前提をQAへ書く。
- Epic公式docs（[MRQ概要](https://dev.epicgames.com/documentation/en-us/unreal-engine/movie-render-pipeline-in-unreal-engine)／[高品質フレーム描画ガイド](https://dev.epicgames.com/documentation/en-us/unreal-engine/rendering-high-quality-frames-with-movie-render-queue-in-unreal-engine)、UE 5.8、2026-11-05参照）の出力設定表は`.bmp`/`.jpg`/`.png`/`.exr`/`.wav`のみでMP4の記載が無い。これは**文書の不在**であり、機能の不存在も非推奨という公式見解でもない。

推奨開始preset（実装済みassetではない）：`vertical`（縦動画・ループ）と`landscape`（横動画）。**presetの数値は`templates/CAPTURE-PRESETS.json`だけが持つ**（解像度・fps・秒数・開始番号・桁数・codec/crf）。frame数は`fps × 秒数`で導出する値であり、定義ファイルにも文書にも第2の値として書かない。frame範囲は終端排他とし重複frameを作らない（機械的な検出は画像列検査の`checks.frame_variety`。既定は`unverified`で、呼び出し側が宣言したときだけpass/failになる。「同一frameの検出」節）。色空間/露出/warm-up/AA/seed/音の有無を記録。MRQ画像列→既存ffmpegでH264/yuv420p、必要音はAAC/48kHzへ。既存encoderがなければ勝手に導入しない。

presetの数値を手で書き写さない。次の1コマンドが、そのpresetの検査範囲・encodeコマンド・ffprobeコマンド・尺の検査コマンドを定義から生成して表示する（renderもencodeもしない）。

```powershell
.\scripts\Get-UECaptureEncodePlan.ps1 -Preset vertical
```


## エンコード前の画像列検査

MRQの終了通知・exit 0・MP4のframe数は、いずれも元画像列そのものの正しさを証明しない。通知が成功していても、画像列に欠番や余分なframeが混じれば、その後のencodeは静かに別の映像になる。MP4側でframe数を1つ確かめても、「元画像列に余分な1枚がある」ことを排除できない。

そこでencodeの前に、期待範囲と実際の画像列を照合する。`scripts/Measure-UERenderArtifacts.ps1`は読み取り専用のhelperで、対象dirを改名・修復・削除しない。**そのため命名は画像を直して合わせるのではなく、render前に決めた命名契約を同じ値でhelperへ渡して合わせる**（下の「命名契約」）。引数の`-StartNumber` / `-EndNumberExclusive` / `-ExpectedWidth` / `-ExpectedHeight`は、`Get-UECaptureEncodePlan.ps1`が出す`FRAMES-CHECK`行からそのまま取る（preset定義の値であり、render範囲を手で書き写さない）。

**検査中の入力変化（DOT-3403）**：helperは各frameのSHA-256を取ってからdecodeするため、その間に別のwriterがdirへ追加・削除・置換すると、`frames[].sha256`は旧bytes、decode結果は新bytesという混在reportになりうる。そこでdecode完了後にdirを再列挙し、範囲内frameのSHA-256を取り直して、名前集合とdigestが変わっていないかを`checks.input_stability`と`input_stability`（`changed` / `added` / `removed` / `unverifiable`）に記録する。変化を1件でも観測したら`input_changed_during_check`を`failures[]`に積み、総合は`fail`（exit 1）で`pass`にならない。再確認できない項目（再hash不能など）が残れば`unverified`。これは**検出であってsnapshotでもlockでもない**：helperは入力を開いたまま保持せず、コピーも排他lockもしない。2回の読取の間で元に戻された変更や、再確認より後の変更は見えない。`pass`は「変化を観測しなかった」以上を意味しない。変化を検出したら、書込み元（render・同期・別agent）を止めてから検査をやり直す。helperは入力を修復・削除・改名・書込みしない。

```powershell
.\scripts\Get-UECaptureEncodePlan.ps1 -Preset vertical
# 出力された FRAMES-CHECK 行を、そのまま実行する。行の形は次のとおり（数値は出力から取る）:
.\scripts\Measure-UERenderArtifacts.ps1 -FramesDirectory '<project>\Out\run_<runid>\frames' `
  -StartNumber <EXPECT の range 開始> `
  -EndNumberExclusive <EXPECT の frame 数 = 終端排他> `
  -ExpectedWidth <EXPECT の幅> `
  -ExpectedHeight <EXPECT の高さ> `
  -NamePrefix '<MRQ の File Name Format が index の前に書く固定文字列。例 Shot0001.>' `
  -Digits <MRQ の Zero Pad Frame Numbers。既定の4など> `
  -RunId '<runid>' `
  -SourceRevision '<template commit>' `
  -ReportPath '<project>\Out\run_<runid>\evidence\frames-check-<attempt>.json' `
  -RenderExitCode <MRQの実終了code。実値がある場合だけ渡す。例 0>
```

**`-RenderExitCode`は、MRQ（またはそれを起動したprocess）の実際の終了codeが手元にある場合だけ渡す。渡さないのが既定で、そのとき`checks.render_exit`は`unverified`、総合verdictも`unverified`（exit 2）になり、passへ上がらない**（render通知/exitの判定欄が空のままpassを名乗らせないため）。`-RenderNotification`は通知本文の記録専用で、本文の意味（`failed`等の語）は解釈せず、単独ではpassを生まない。

`<...>`を`Get-UECaptureEncodePlan.ps1`の出力で埋める。この文書にpresetの数値を書かないのは、一度書くと定義と文書の二重管理になり、片方だけ直したときに黙って食い違うためである。

`-FrameStep` / `-FrameNumberOffset` は MRQの `Output Frame Step` / `Frame Number Offset` の実値を書き写す。既定（1と0）は従来の連番と同じ。

### 画像列検査の再実行（reportの名前）

report pathは**attemptごとに別file**にする: `evidence\frames-check-<attempt>.json`。`<attempt>`は同じ`run_<runid>`内の画像列検査の回数で、1から始める。helperは既存reportを上書きせず、書かずに拒否する（終了code 3）。したがって同じ`run_<runid>`で再renderして再検査するときは、`<attempt>`を1つ増やした新しいpathへ書く（`Get-UECaptureEncodePlan.ps1`の`FRAMES-CHECK`行は`<attempt>`を埋めるだけでそのまま使える）。

**既存reportを現在のframesの証拠として引用しない。** 現在の`frames/`に対応するreportは、番号が最大のattemptだけである。番号の小さいreportはそのattemptの時点の履歴であり、削除も上書きもしないが、QAの証拠欄へ現在の結果として書かない（1回目がpassでも、再render後の`frames/`についてはpassを意味しない）。QAの証拠欄には、実際に使ったfile名（attempt番号込み）と、そのreportの`generated_at_utc`・`observed.contract_file_count`を書く。この規則の正本はこの節だけで、`README.md`と`templates/QA.md`はこの節を指す。

### 命名契約（`-NamePrefix` / `-Digits`）

**helperの命名契約はrender前に決める。** MRQの`File Name Format`と`Zero Pad Frame Numbers`の実値をQA（`templates/QA.md`の`QA-IMG-01`）へ記録し、同じ値を`-NamePrefix` / `-Digits`としてhelperへ渡す。render後に画像を改名して合わせない（入力を書き換えない契約を保つ）。

- MRQは`<sequence_name>.<frame_number>.png`のように、**index（数字）の前に必ず名前を付ける**。Epic公式docsは`File Name Format`を「export名のformat string」、`Zero Pad Frame Numbers`を「出力frame番号を何桁にpadするか（2なら`_01`、4なら`_0001`）」と説明するだけで、既定値は書いていない。既定値はUE 5.8.4同梱のMRQ plugin sourceの読取りによる：legacy Output Settingは`{sequence_name}.{frame_number}`・4桁（`MoviePipelineOutputSetting.cpp`）、Movie Graphのfile outputは`{sequence_name}.{layer_name}.{frame_number}`・4桁（`MovieGraphFileOutputNode.h` / `MovieGraphGlobalOutputSettingNode.cpp`）。UIの桁数は1〜5で、6は選べない。**この既定は実render出力の観測ではなく、source読取りからの推論**である（実renderでの確認は未検証）。
- `-NamePrefix`は、indexの前に付く固定文字列そのもの（例: legacy既定なら`Shot0001.`、Movie Graphなら`Shot0001.Deferred.`）。省略すると前置き無しの`<digits>.png`だけを受理する従来の契約になる。helperは前置きを推定しない。
- `-Digits`は桁数。helperの既定は6だが、これは**MRQの既定ではなく、このhelperが従来から持っていた値**を後方互換のために残したもので、engine既定（4）ともUI上限（5）とも一致しない。MRQの実値を必ず渡す。既定のまま渡してよいのは、画像列をその桁数で別に用意している場合だけである。
- 例（legacy既定・240frame）: `-NamePrefix 'Shot0001.' -Digits 4`は`Shot0001.0000.png`〜`Shot0001.0239.png`をpassする。

- 期待枚数だけでなく、全対象ファイルの番号集合を照合する。先頭・中間・末尾の欠番、範囲外の余分なframe、桁数/拡張子の揺れ、想定外の名前、0 byte、decode不能、解像度不一致、同一frameの重複・全編同一（止まり。既定は報告だけで、判定は宣言時のみ）を検出する。
- `-Extension`は省略時`.png`。EXR列を検査するときは必ず`-Extension .exr`を渡す。既定のままEXR列を渡すと、EXR frameを想定外の名前、期待するPNG frameを欠番として報告し、正しい列をfailにしてしまう。
- **`-Extension`は命名だけでなくcodec契約も決める。** helperは各frameをdecodeしてffprobeが返すcodec名を、拡張子から決まる期待codecと照合する。不一致（例: `.jpg`名で1枚だけ中身がPNG、PNG bytesを`.exr`名で保存）は`codec_mismatch`としてfileとcodecを名指しし、decode=`fail`・verdict=`fail`にする。拡張子は大小無視で次の表に引く。

  | `-Extension` | 期待codec（ffprobeの`codec_name`） |
  |---|---|
  | `.png` | `png` |
  | `.jpg` / `.jpeg` | `mjpeg` |
  | `.bmp` | `bmp` |
  | `.exr` | `exr` |

  表に無い拡張子（例`.tif`）は拒否せず命名・欠番・サイズは検査するが、codecを検査していないため`codec_not_configured`を報告し、decode=`unverified`・総合verdict=`unverified`（exit 2）にしてpassにしない。helperは拡張子を推定せず、改名もしない。期待codecはreportの`input.expected_codec`と`expectations.codec`（未定義なら`not_configured`）、観測codecは`frames[].codec`に残る。`.exr`の期待codec名`exr`は、この表を作った環境のffprobe 8.1.2での観測で、他版の表記は未確認。`.jpg`の実MRQ出力の画素形式・綴りは実renderでしか確定しない。これは「拡張子と非空サイズだけで合格にしない」の画像列側の実装範囲であり、`.png`の判定は従来から変わらない。
- 入力は明示する。`-StartNumber`は0以外も指定できるが、render範囲から書き写す。`-EndNumberExclusive`は終端排他。解像度を省くと解像度判定は`unverified`になり、passにならない。

- 入力は明示する。`-StartNumber`は0以外も指定できるが、render範囲から書き写す。`-EndNumberExclusive`は終端排他。解像度を省くと解像度判定は`unverified`になり、passにならない。**presetを使う場合は`Get-UECaptureEncodePlan.ps1`の`FRAMES-CHECK`行をそのまま使い、数値を文書から転記しない。**
- decodeは既存環境の`ffprobe`を使うだけ。PATHに無い場合は`-DecoderPath`で既存実体を明示する。decoderが無い・失敗・timeoutのときはdecode=`unverified`または`fail`であり、総合passにしない。timeoutは既定10秒で、その場合も成功へ丸めない。**本物のdecode失敗（`decode_failed`・`codec_mismatch`）とtimeoutが同時にあるときは`fail`が勝つ。** timeoutは「失敗が無いときだけ」`unverified`にする（`decode_failed`は`failures[]`に残るので、reportの本文と`artifact_verdict`は食い違わない）。timeoutしたframeは新しいprocessで1回だけ再試行し、各frameの`attempts`をreportに残す（再試行で復号できれば`ok`・`attempts=2`で、握り潰さず記録する。2回とも超過なら`timeout`のまま`unverified`）。`-TotalDecodeBudgetMilliseconds`（既定300000＝5分。CIの`timeout-minutes: 20`に収まるよう安全側）で全probe（再試行込み）の総予算を指定でき、超過は`pass`にも`fail`にも丸めず`decode_budget_exhausted`を`failures[]`に積んだ`unverified`にする。reportの`decode_summary`に評価したframe数・評価しなかったframe数・各状態の内訳・再試行数・予算を残す。
- reportは新規の明示出力先だけに書き、既存fileを上書きしない。文字列上の内部pathに加え、`FramesDirectory`またはreport親pathの既存componentにjunction/symlink等のreparse pointがある場合は、実効境界を安全に照合できないため入力検査・親dir作成より前に拒否する。reportを画像列dirの外側にある通常のdirectoryへ書く。helper自身は入力を書き換えず読み取りだけを行うが、各frameを読んでper-frame SHA-256を計算し、`frames[].sha256`と`frames[].digest_state`（`computed` / `not_computed`）としてreportに書く。`computed`のときだけ`sha256`は小文字hex 64桁の実digestで（0 byte fileも空bytesのSHA-256として計算する）、計算できなかった場合は`sha256: null`と`not_computed`で、空文字やplaceholderは書かない。このdigestはその実行中に読んだbytesの識別であり、検査中に他者が入力を変えていないことの証明ではない（reportの`notes`の"read only"も同様に、helperが書き込まないことの説明であって外部変更の否定ではない）。digestが実fileと一致すること、定数・空文字の退行をfile名とindexで落とすことは回帰suiteが固定している。「入力が変わっていない」ことは回帰suite `scripts/Test-UERenderArtifacts.ps1` が検証する：suiteが作った18のfixtureディレクトリすべてについて、構築直後の全file名・SHA256をbaselineとして記録し、末尾で再比較して**追加・削除・内容変更をpathで名乗り上げる**。また`reports/`は件数と非空を別途照合し、`Production/`配下の無視される残骸も直接列挙する（`git status --untracked-files=all`は`.gitignore`の`Production/*`を見ないため、これだけでは不十分）。このgate自体が空assertに戻らないよう、「fixtureを壊せばsuiteはそのpathを名指しで落ちる」ことをsuite内の負例groupで固定する。2つのguardは片方だけ外したときに落ちることを別々の負例fixtureで固定する：report親だけをjunctionにしたfixtureと、`FramesDirectory`だけをjunction aliasにしreport親を実体の通常directoryにしたfixtureである。後者は、`FramesDirectory`側のguardを外すとreportがalias経由で検査対象dirに書かれ、そのguardを戻すと書込み前に拒否される（拒否理由が`ReportPath parent`ではなく`FramesDirectory`であることまでassertする）。
- reportは同じ親directory内の実行固有の一時file（`.<report名>.<guid>.tmp`）へ全bytesを書き、flushが成功した後だけ最終ReportPathへ上書きなしでmoveして公開する。書込途中に失敗しても最終ReportPathには何も公開されず（不完全JSONを残さない）、この実行の一時fileはbest-effortで削除し、既存reportは変更しない。公開直前に最終名へ別のreportが現れた場合も、そのreportをbyte単位で保持して失敗する。強制process killなどで中断した場合の一時fileの削除までは保証しない。その残骸は`.tmp`で`.json`ではないので、有効なreportとして扱わない。回帰suiteは環境変数`UE_RENDER_QA_TEST_FAULT`（テスト専用、未設定なら無効）で書込途中の失敗と公開時の競合を注入して固定する。このPowerShell testはUE 5.8.4のcompile/PIE/MRQ/render/ffprobe実映像検査の成功を意味しない（Unverified Scope）。

- **前置き付きの画像列を宣言なしで渡すと`naming_contract_mismatch`になる。** 前置きが違うだけで枚数もindexも正しい画像列を「240枚欠番」と読んで再renderしないために、helperは1枚も契約に合わないとき、残りが1通りの`<prefix><n桁>`の形にそろっていれば、それを`naming_contract_mismatch`として報告し、一致させる`-NamePrefix` / `-Digits`を詳細に出す（`missing_frames`は主因にしない）。報告だけで、観測した形を採用して通すことも改名もしない。確認した上で、MRQの実値を書き写して再検査する。0枚が契約に合ったとき、decode/resolutionは`fail`ではなく`unverified`（何もdecodeしていない）。
- **MRQの`Output Frame Step`を使ったrenderは、連番ではなく格子で出力される。** `-FrameStep`と`-FrameNumberOffset`（既定は1と0＝従来の連番）で、期待するindexの格子を宣言する。step=2・240frame範囲なら期待indexは`0,2,4,…,238`の120枚で、`-FrameStep 2 -EndNumberExclusive 240`がpassする。宣言しないと、helperは格子の不一致を`index_lattice_mismatch`として報告する（実ファイルが公差2の等差数列で、宣言stepが1のとき）。この場合の欠番は「画像列の欠落」ではなく「宣言格子の食い違い」であり、`missing_frames`を主因にしない。**MRQの`Output Frame Step` / `Frame Number Offset`はQAへ実値を記録し、同じ値をhelperへ渡す。** 推測でstepを決めない。
- **`Handle Frame Count`は宣言rangeの外へ連続frameを足す。** 連続なので`index_lattice_mismatch`ではなく`out_of_range_frames`になる。handle込みが納品対象なら宣言rangeを広げる。どちらを納品したかをQAに書く。
- decodeは既存環境の`ffprobe`を使うだけ。PATHに無い場合は`-DecoderPath`で既存実体を明示する。decoderが無い・失敗・timeoutのときはdecode=`unverified`または`fail`であり、総合passにしない。timeoutは既定10秒で、その場合も成功へ丸めない。**本物のdecode失敗（`decode_failed`・`codec_mismatch`）とtimeoutが同時にあるときは`fail`が勝つ。** timeoutは「失敗が無いときだけ」`unverified`にする（`decode_failed`は`failures[]`に残るので、reportの本文と`artifact_verdict`は食い違わない）。timeoutしたframeは新しいprocessで1回だけ再試行し、各frameの`attempts`をreportに残す（再試行で復号できれば`ok`・`attempts=2`で、握り潰さず記録する。2回とも超過なら`timeout`のまま`unverified`）。`-TotalDecodeBudgetMilliseconds`（既定300000＝5分。CIの`timeout-minutes: 20`に収まるよう安全側）で全probe（再試行込み）の総予算を指定でき、超過は`pass`にも`fail`にも丸めず`decode_budget_exhausted`を`failures[]`に積んだ`unverified`にする。reportの`decode_summary`に評価したframe数・評価しなかったframe数・各状態の内訳・再試行数・予算を残す。
- reportは新規の明示出力先だけに書き、既存fileを上書きしない。文字列上の内部pathに加え、`FramesDirectory`またはreport親pathの既存componentにjunction/symlink等のreparse pointがある場合は、実効境界を安全に照合できないため入力検査・親dir作成より前に拒否する。reportを画像列dirの外側にある通常のdirectoryへ書く。helper自身は入力を書き換えず読み取りだけを行うが、各frameを読んでper-frame SHA-256を計算し、`frames[].sha256`と`frames[].digest_state`（`computed` / `not_computed`）としてreportに書く。`computed`のときだけ`sha256`は小文字hex 64桁の実digestで（0 byte fileも空bytesのSHA-256として計算する）、計算できなかった場合は`sha256: null`と`not_computed`で、空文字やplaceholderは書かない。このdigestはその実行中に読んだbytesの識別であり、検査中に他者が入力を変えていないことの証明ではない（reportの`notes`の"read only"も同様に、helperが書き込まないことの説明であって外部変更の否定ではない）。digestが実fileと一致すること、定数・空文字の退行をfile名とindexで落とすことは回帰suiteが固定している。「入力が変わっていない」ことは回帰suite `scripts/Test-UERenderArtifacts.ps1` が検証する：suiteが作った23のfixtureディレクトリすべてについて、構築直後の全file名・SHA256をbaselineとして記録し、末尾で再比較して**追加・削除・内容変更をpathで名乗り上げる**。また`reports/`は件数と非空を別途照合し、`Production/`配下の無視される残骸も直接列挙する（`git status --untracked-files=all`は`.gitignore`の`Production/*`を見ないため、これだけでは不十分）。このgate自体が空assertに戻らないよう、「fixtureを壊せばsuiteはそのpathを名指しで落ちる」ことをsuite内の負例groupで固定する。
- reportは同じ親directory内の実行固有の一時file（`.<report名>.<guid>.tmp`）へ全bytesを書き、flushが成功した後だけ最終ReportPathへ上書きなしでmoveして公開する。書込途中に失敗しても最終ReportPathには何も公開されず（不完全JSONを残さない）、この実行の一時fileはbest-effortで削除し、既存reportは変更しない。公開直前に最終名へ別のreportが現れた場合も、そのreportをbyte単位で保持して失敗する。強制process killなどで中断した場合の一時fileの削除までは保証しない。その残骸は`.tmp`で`.json`ではないので、有効なreportとして扱わない。回帰suiteは環境変数`UE_RENDER_QA_TEST_FAULT`（テスト専用、未設定なら無効）で書込途中の失敗と公開時の競合を注入して固定する。このPowerShell testはUE 5.8.4のcompile/PIE/MRQ/render/ffprobe実映像検査の成功を意味しない（Unverified Scope）。
- 終了codeはpass=0、fail=1、unverified=2。**引数拒否（範囲不正・解像度の片側指定・`FramesDirectory`が無い・report pathが既存・reportが画像列dirの内側・reparse point・整数でない`-RenderExitCode`）はすべて、reportを書かずに終了code 3で終わる**。exit 1はreportが書かれ`artifact_verdict`が`fail`のときだけで、reportの無いexit 1は無い（reportの不存在を成果物のfailの根拠にしない）。**`-RenderExitCode`が整数として読めない値（`unknown`・`1.5`・`0x1`など）は引数拒否で、reportを書かずに終了code 3で終わる**（artifactのfail=1とも、unverified=2とも別。値は検証してからreportへ書くので、非数値が観測された終了codeとして残らない）。負の整数も整数として受理し、0以外なのでfailにする。

### 同一frameの検出（`frame_variety`）

- 「重複frameを作らない」（frame範囲の契約）は、これまで文書だけで、240枚がすべてbyte同一でも画像列検査は全checkをpassにしていた。helperは既に全frameのSHA-256（`frames[].sha256`）を計算しているので、その出現回数を1回数えるだけで同一性を報告する。追加のhash計算はなく、frame同士の総当たり比較もしない（O(n)）。
- `observed`に`distinct_frame_hashes`（異なるdigestの数）、`duplicate_frames`（他のframeとdigestを共有するframe数）、`duplicate_groups`（そのdigestの数）、`duplicate_group_samples`（group毎のindexとfile名。最大10 group・各20件の抜粋で、件数は全数）、`longest_identical_run`（index順で隣り合う同一digestの最長連続数＝frameの止まり）が出る。digestを計算できなかったframeは数えず、連続も切る。
- **`checks.frame_variety`の既定は`unverified`。** 止め絵・タイトルカードは正当な成果物で、「重複＝失敗」とは資料だけでは言えず、repoは閾値を持たない。だから宣言したときだけpass/failになる。`unverified`のままなら総合verdictにも参加しない（従来の呼び出しの終了codeは変わらず、`failures`にも出ない）。

  | 宣言 | `frame_variety` | 意味 |
  |---|---|---|
  | なし | `unverified` | 数だけ報告する。passにしない |
  | `-ExpectedMinDistinctFrames <n>` | n個以上distinctなら`pass`、未満なら`fail`（総合verdictも`fail`、exit 1、`frame_variety_below_expected`） | 全frameのdigestが取れていない状態で未満なら`unverified`。nが期待枚数を超える値と、0以下は入力拒否（exit 3） |
  | `-AllowIdenticalFrames` | `pass` | 静止画列を意図したという宣言を`frame_variety_declaration`へ残す。他のcheckは変わらない。両方の宣言は矛盾なので入力拒否（exit 3） |

- nは案件ごとに決める（repoは既定値を持たない）。動きのある列なら期待枚数に近い値、止め絵を挟む列なら実際のdistinct数を宣言する。**byte digestの同一性だけを見る**ので、見た目が近いだけの別frameは重複にならず、画質指標も使わない。
- 回帰は`scripts/Test-UERenderArtifacts.ps1`の`frame-variety-declared-identical-frames`。240枚同一・239+1・小さな連続列・240枚distinct（実decoderでexit 0）を固定している。

## CIのdecoder固定

CIの`render-artifacts` jobは、runner imageに入っている`ffprobe`をそのまま使わない。`scripts/ffprobe-pin.json`に配布元URL・archiveのSHA-256・`ffprobe.exe`のSHA-256・期待するversion行のprefixを記録し、`scripts/Install-PinnedFfprobe.ps1`がその3点を照合してから検査に使う。以前はPATHに`ffprobe`があれば任意版を受け入れ、無い場合はversion指定なしの`choco install ffmpeg`に落ちていたため、同じcommitでもrunner imageやpackage更新でdecode判定が変わり得た。

- 固定した実体はcheckoutの外（`$env:RUNNER_TEMP`、ローカルでは`%TEMP%\ffprobe-pin`）に置き、template・`Production/`・成果物へ同梱しない。CI内のfixture decodeにのみ使う。
- 取得元は`GyanD/codexffmpeg` 8.1.2 essentials build（GPL-3.0-or-later）。archiveのsha256は`db580001…`、`ffprobe.exe`は`b49ccc7c…`、versionは`ffprobe version 8.1.2-`で始まる行。ライセンスはCI内利用に閉じ、repoの配布条件（`LICENSE-NOTICE.md`）とは別物として扱う。
- `scripts/Test-FfprobePin.ps1`が負例を固定する：manifestの項目欠落・archiveの1 byte改変・PATHの手前に別の`ffprobe`がある場合をすべて拒否し、固定版のbytesとversionだけを受け入れる。suiteはcheckout内に何も書かない。
- 判定ロジック（`Measure-UERenderArtifacts.ps1`のdecode/timeout優先順位）と既存assertionは変えていない。固定したのはdecoderの実体だけ。
- 版を上げる場合は`ffprobe-pin.json`の3つの値（archive sha256・binary sha256・version prefix）を同時に更新し、`Test-FfprobePin.ps1`と`Test-UERenderArtifacts.ps1`を通す。片方だけ更新したmanifestはinstallerが拒否する。

判定は次の5つを独立に扱い、1つの欄でまとめない。

| 判定 | 何を見るか | 何を証明しないか |
|---|---|---|
| render通知/exit | MRQの終了通知・exit code | 画像列の完全性 |
| 画像列 | 番号集合・命名・サイズ・decode・解像度。経路Aの必須項目。経路B（direct-MRQ MP4）は対象が存在しないため、`encode_path`=`mrq-native-mp4`と`source_png_sequence`=存在しないの記録を伴う場合だけ`non-goal`と書き、`unverified`のまま放置しない | render成功・映像の見た目 |
| MP4 | 既存ffprobeで幅/高さ/fps/frame数/秒数/codec/pix_fmt/profile/音声 | 先頭/中間/末尾の見た目 |
| 目視・全編再生 | 0付近/中間/末尾、全編、loop継ぎ目 | 音の内容 |
| 音 | 実聴取。stream存在は聴取ではない | 映像の見た目 |

画像列のfailは、**成果物の不備**（欠番・余分・0 byte・decode不能・解像度不一致）、**宣言格子の不一致**（`index_lattice_mismatch`）、**命名契約の不一致**（`naming_contract_mismatch`。画像列は正しく、渡した`-NamePrefix` / `-Digits`がMRQの`File Name Format` / `Zero Pad Frame Numbers`と違う）を区別して読む。命名契約の不一致は再renderの理由にならない。後者は画像列が壊れているのではなく、helperへ渡したstep/offsetがMRQの実値と違う。原因を切り分ける前にencodeへ進まない。

画像列がpassでも、render成功・全編目視・音・loop品質は別項目のまま`unverified`とする。逆に通知成功/exit 0の記録があっても、画像列の負例をpassへ読み替えない。

**render通知/exitの欄は、画像列検査のreportの`checks.render_exit`と`render_evidence.exit_code`である。** `checks.render_exit`は既定`unverified`（`-RenderExitCode`未指定。通知本文だけでもこのまま）、整数0で`pass`、整数かつ0以外で`fail`。`fail`は総合verdictの最悪状態に参加するので、`-RenderExitCode 1`は画像列の7項目がすべてpassでも`artifact_verdict`=`fail`・process exit 1・`failures`に`render_exit_nonzero`1件になり、artifact側のpassと併記されない。`render_evidence.conclusion`は`evaluated_from_exit_code`（値を与えた）か`not_provided`（与えなかった）で、定数ではない。判定するのは**呼び出し側が宣言した終了codeが0か否か**だけで、画像列から実renderの成功は導かない（`render_artifacts_cannot_prove_render_success`は常に`true`）。実MRQが非0を返したときその値がこの引数へ正しく渡るかはUE実機では未観測（Unverified）。

旧runの同数frameが混入していないことは、この検査だけでは判定できない。run専用の新規出力先と所有権照合を前提にする。

## エンコードとMP4の尺検査

上の1コマンドを実行すると、そのpresetの`EXPECT`行（frame数・秒数・解像度・fps・範囲）、`FRAMES-CHECK`・`FFMPEG`・`FFPROBE`・`INSPECT`の各コマンドが、すべて`templates/CAPTURE-PRESETS.json`から導いて表示される。ここに数値例を貼らないのは、貼った瞬間に定義と二重管理になるためである。`frames/`・`Out/final`・`Out/run_<runid>/evidence/`は当該run内のpathに読み替える。

**`-frames:v`は出力frame数の上限であり、尺の検証手段ではない。** 元の画像列がその数より少なければ、ffmpegは少ないままencodeして**exit 0で成功を返す**。したがって「encodeがexit 0だった」「ffprobeが報告した秒数がそれらしかった」のどちらも、presetの尺を満たした証明にならない。`vertical`用のencodeコマンドを`landscape`（10秒尺）にそのまま当てると、短いMP4が成功として得られる。尺の検証は、次の検査器がpreset定義の期待frame数・秒数を実測と照合して行う。

**`ffmpeg -n`は出力が既存だと何も書かずに終わり、終了statusは0になりうる。** 公式docsは「exit immediately」とだけ述べ、終了statusの値は規定していない。本hostの実測（ffmpeg 8.1.2 gyan.dev build）ではstderrに`already exists. Exiting.`が出てprocess exitは0である。別build（GitHub Actions runner）では-17を返す。exit codeの値に依存せず、更新時刻で判定する。再renderのあとに同じencode行を同じ出力先へ流すと、前回のMP4が残ったまま成功扱いになり、そのffprobeは前回の240 frame / 8.0 sを正しく報告する。frame数と秒数が合っていても今回のrenderの検品にはならない。次の規則で塞ぐ。

- encode出力先は**attemptごとに新しいpath**にする（例: `Out/run_<runid>/final/clean_<attempt>.mp4`）。根拠なく`-y`を既定にしない。既存の採用版を潰すためである。`-y`を使うなら、run内で一意な出力先を同時に要求する。
- renderを始める**直前**にUTCのmarkerを採る（`$renderStartedUtc = (Get-Date).ToUniversalTime().ToString('o')`）。
- 検査器へ`-RenderStartedUtc`と`-FramesDirectory`を渡す。MP4の更新時刻がmarkerより古い、またはmarkerより古い画像が残っていれば`fail`にする。どちらかを渡さなければ`unverified`で、passにしない。

```powershell
$renderStartedUtc = (Get-Date).ToUniversalTime().ToString('o')   # renderの直前に採る
.\scripts\Measure-UECaptureEncode.ps1 -Preset landscape -VideoPath '<project>\Out\run_<runid>\final\clean_<attempt>.mp4' -ReportPath '<project>\Out\run_<runid>\evidence\encode-check.json' -RenderStartedUtc $renderStartedUtc -FramesDirectory '<project>\Out\run_<runid>\frames'
```

- 期待値は`templates/CAPTURE-PRESETS.json`のpreset定義から導き、コマンド引数で期待frame数を渡さない。手書きの期待値を渡せる経路を作らないためである。
- 照合するのはvideo stream数（ちょうど1本）、`nb_read_frames`、`duration`、`width`/`height`、`r_frame_rate`。frame数は`fps × 秒数`から導出し、定義側に第2の値として書かせない（書かれていれば`preset_invalid`で落とす）。
- 由来の照合は`render_attempt`（MP4の更新時刻 >= marker）と`source_frames_fresh`（markerより古い画像が0枚）の2項目で、更新時刻の比較だけを行う。中身の正しさは保証しない。古いMP4のままの再encode・旧render残骸の上に少数の新frameを書いた混在・markerなしは、いずれもpassにならない。ffprobeがexit 0以外を返す（対象欠落・壊れたfile）場合は`probe_failed`で`fail`になる。
- 元画像列の集合契約（命名・offset・range・欠番）は`Measure-UERenderArtifacts.ps1`の担当で、本検査は「MP4が古い・混在している」ことを`fail`にするだけである。
- 不一致は`fail`（exit 1）、測れない（ffprobe不在・timeout・stream数不一致で読めない）は`unverified`（exit 2）で、どちらもpassにしない。reportは新規pathにだけ書き、検査対象のMP4を変更しない。
- この検査はMP4の内容だけを見る。元画像列の集合（欠番・範囲外）は`Measure-UERenderArtifacts.ps1`の担当で、両方を別項目として記録する。
- 回帰は`scripts/Test-UECaptureEncode.ps1`。自作fixtureで「300 frame presetを240 frameでencodeするとexit 0のまま`fail`」「正しい300 frameは`pass`」「299 frameは`fail`」「ffprobe不在は`unverified`」「video stream 2本は`fail`」に加えて、「既存MP4へ`-n`で再encode（exit 0・未更新）は`fail`」「旧render残骸＋少数の新frameは`fail`」「途中欠番は`fail`」「読めないMP4は`fail`」「markerなし・未来のmarker・frame directoryなしは`unverified`」を固定している。

**連番の画像列（step=1）:** `%06d`は**一例であって既定ではない**。`-i`のtemplateはMRQの実名に合わせる（`File Name Format`の前置きと`Zero Pad Frame Numbers`の桁数。helperへ渡した`-NamePrefix` / `-Digits`と同じ値）。たとえばMRQ legacy既定の`Shot0001.0000.png`〜なら`-i frames/Shot0001.%04d.png`で、本hostでは同じ240枚に`%06d`は開けず（`No such file or directory`、exit 127）、`Shot0001.%04d`は240 frameのMP4を返した。

```text
ffmpeg -n -framerate 30 -start_number 0 -i frames/Shot0001.%04d.png -frames:v <EXPECT.frame_count> -c:v libx264 -pix_fmt yuv420p -crf 18 -movflags +faststart Out/final/clean_<attempt>.mp4
# 前置きの無い6桁の画像列なら:
ffmpeg -n -framerate 30 -start_number 0 -i frames/%06d.png -frames:v <EXPECT.frame_count> -c:v libx264 -pix_fmt yuv420p -crf 18 -movflags +faststart Out/final/clean_<attempt>.mp4
ffprobe -v error -count_frames -show_entries stream=index,codec_type,codec_name,profile,level,width,height,pix_fmt,bits_per_raw_sample,r_frame_rate,nb_read_frames,color_range,color_space,color_transfer,color_primaries,sample_rate,channels -show_entries format=duration,size -of json Out/final/clean_<attempt>.mp4
```

**RECEIPT-PIXFMT-RULE（宣言と実測の照合。この規則の正本はここ1箇所）:** 経路Aの宣言「H.264/yuv420p」は、上のffprobe受領証の`pix_fmt`の実測が`yuv420p`であることをもってのみ満たされる（presetが別の形式を定義する場合は`templates/CAPTURE-PRESETS.json`の`pix_fmt`の値。未記載はyuv420p）。実測が異なる成果物は採用しない。宣言を書き換えるか、encodeし直す。`scripts/Measure-UECaptureEncode.ps1`が`pixel_format`欄でこれを照合し、不一致は`pixel_format_mismatch`で`fail`（exit 1）、`pix_fmt`を読めなければ`unverified`（exit 2）にする。経路Bで得たMP4にも同じ受領証を使う。`profile`・`level`・`bits_per_raw_sample`・`color_range`・`color_space`・`color_transfer`・`color_primaries`は記録項目で、ffprobeが出さない項目は`unknown`と書く（空欄・省略でpassにしない。reportも`unknown`で残す）。色情報の値は期待値と照合しておらず、再生互換性の判定でもない。

**`-pix_fmt`は強制ではない。** FFmpeg公式docs（`-pix_fmt`、2026-11-08取得）は、選んだpixel formatが選べない場合ffmpegは警告を出してencoderが対応する最良の形式を選ぶこと、`-pix_fmt`の前に`+`を付けた場合だけ選べなければエラー終了することを述べている。実測（本host、ffmpeg 8.1.2 gyan.dev build、1080x1920 / 30fps / 24 frameのPNG列）では、`-pix_fmt yuv420p`は`yuv420p` / `High`、`-pix_fmt`を落とすと`yuv444p` / `High 4:4:4 Predictive`、`-pix_fmt yuv420p10le`は`yuv420p10le` / `High 10`、`-pix_fmt rgb24`（libx264非対応）はstderrに`Incompatible pixel format 'rgb24' for codec 'libx264', auto-selecting format 'yuv444p'`を出してexit 0で`yuv444p`になった。`pix_fmt`と`profile`を持たない旧受領証は、この4通りが`format.size`を除いて同一だった。

既定の手順は**encode後の照合**（上のffprobe受領証＋inspector）で、`-pix_fmt +yuv420p`は既定にしない。同じhostのffmpeg 8.1.2ではPNG入力に`-pix_fmt +yuv420p`を付けるとexit -22（`automatic conversion is disabled`）で止まり、`-vf format=yuv420p`を併記しても同じだったため、そのままでは使えない。`+`を足せる版では、fallbackをencodeの時点で止める補助として任意に足してよいが、encode後の照合は外さない。

**格子の画像列（step=2）:** image2の`%06d`連番templateは**最初の欠番で入力を終える**。`-i`の`%06d`に格子をそのまま渡すと、ffmpegは**exit 0で1frameのMP4**を作る（stderrにerrorは出ない）。実測（本host、ffmpeg 8.1.2、120枚のstep-2格子）では`FFMPEG_EXIT=0`・`nb_read_frames=1`・`duration=0.033333`。尺が1frameでも成功終了するので、ffprobeのframe数を必ず見る。

格子をencodeするときは、**当該runの新しい出力先**へ連番に振り直した複製を作り、そこを`-i`に渡す（検査対象の画像列は改名しない）。

```text
# 1) 格子を連番へ振り直す（元の画像列は変更しない）
$i = 0; Get-ChildItem '<frames>' -Filter *.png | Sort-Object Name | ForEach-Object { Copy-Item $_.FullName (Join-Path '<renumbered>' ('{0:D6}.png' -f $i)); $i++ }

# 2) 振り直した連番をencode。frame数は step 倍率で減るので -frames:v は格子の枚数に合わせる
ffmpeg -n -framerate 30 -start_number 0 -i '<renumbered>/%06d.png' -frames:v <declared_lattice_count> -c:v libx264 -pix_fmt yuv420p -crf 18 -movflags +faststart Out/final/step2_<attempt>.mp4
ffprobe -v error -count_frames -show_entries stream=nb_read_frames,r_frame_rate -show_entries format=duration -of json Out/final/step2_<attempt>.mp4
```

実測（本host、ffmpeg 8.1.2、120枚）：振り直し後は`FFMPEG_EXIT=0`・`nb_read_frames=120`・`duration=4.000000`（`-framerate 30`）。同じ格子を`-framerate 15`で読むと`nb_read_frames=120`・`duration=8.000000`。**stepで間引いたrenderは実時間より短く出るので、どちらの尺を納品したかをQAに書く。** 等倍で見たいなら`-framerate`を元fpsの1/stepにし、尺をffprobeで確認する。この`-frames:v`は出力上限であり、元画像列の整合性はhelperの判定で担保する（DOT-3217のlandscape切り落としとは別項目）。

`-pattern_type glob`はWindowsの一部buildで未対応（本hostのffmpeg 8.1.2は`globbing is not supported by this libavformat build`でexit -40）。`concat`demuxerは1枚1frameの`-r`を明示しないと3〜4frameで止まる（同buildで実測）。**どちらも格子のencode手段として使わない。**

音あり版は同期・尺を合わせ、採用音の権利を確認。音声streamの存在は聴取確認ではない。
公式MRQ： https://dev.epicgames.com/documentation/en-us/unreal-engine/movie-render-pipeline-in-unreal-engine

## Play / 展開版チェック

- 起動map・Pawn・開始姿勢。座位/立位が仕様なら両方。
- mouse視点、移動、zoomの往復、台や壁のcollision、外周の落下/抜け、Rリセット、H help、Esc/終了。未実装の機能は合格にせず仕様上の非対象と区別。
- 最新版で5分以上の連続鑑賞。測定時間・操作/無操作の内訳、hardware、解像度、品質、frame time平均/スパイクを記録し、「観測方法」は次の3項目に分けて書く（**Performance record contract**）。
  - `measured_build_config`: `Editor` / `Development` / `Shipping` のいずれか。複数のconfigを測るなら記録を分ける。Editor PlayやDevelopmentの値を「Shippingの性能」として書かない。
  - `instrument`: 閉じた語彙。`engine-statunit`（engine内`stat unit`）/ `engine-fpschart`（engine内FPS chart）/ `engine-startfile`（`stat startfile`）/ `external-capture`（OS・GPU側の外部キャプチャ）/ `manual-or-unknown`（手入力・不明）/ `none`。
  - `artifact`: 数値の出所ファイルのpath。無ければ`none`と書く。`none`は合格根拠にならず、`none`のまま数値だけを書いた記録は出所不明の`unverified`になる。
  - 規則: **`Shipping`を測ったと書くなら、そのconfigで成立する計測器でなければならない。** UE 5.8.4のEngineソース読取（静的事実。実Shipping buildでの実行確認ではない）では、Shippingの既定は`stat unit`の入力経路（`ALLOW_CONSOLE`）、FPS chartの出力（`ALLOW_DEBUG_FILES`・`!UE_BUILD_SHIPPING`）、`stat startfile`（`STATS`）のいずれも無い。したがって`Shipping`で使えるのは`external-capture`だけで、`Shipping`+`engine-*`は不成立（fail）。Developmentで測るなら`Development`と書く。targetが`bUseConsoleInShipping`等を明示的に有効にしている場合は別で、本規則は既定値の契約。
  - 機械判定: `scripts/Test-UEPerformanceRecord.ps1`（`-RecordPath`にJSON1件または配列、または`-BuildConfig`/`-Instrument`/`-Artifact`/`-MeasuredAt`）。不成立の組=fail(exit 1)、`instrument`が`none`/`manual-or-unknown`/空・`artifact`が`none`/空・`measured_at`空=unverified(exit 2、総合合格にしない)、成立する組=pass(exit 0)。判定は**記録の帰属**であり、数値の妥当性ではない。
- FPS目安は案件ごとに合意。初期提案は最低30fps（33.3ms）、目標60fps（16.7ms）。これは測定実績でも共通保証でもなく、`measured_build_config`と`instrument`を伴う記録でだけ意味を持つ。
- 過去Bonfire play8は720p平均13.7〜14.8ms、144.5ms hitchを1回報告。**計測器・build configが記録に無いため、別host/別版へ転用しない（転用不可）。** 過去記録は書き換えない。
- Shipping ZIP別展開→起動・操作を再確認。Editor PlayだけではShippingの入力/終了を証明しない。
- **`extracted-check/`と納品物のhash照合**：`SHA256SUMS.txt`と納品artifactは同一dirに置き、検証はそのdirで行う。`extracted-check/`の中や、同名の古い複製があるdirで`sha256sum -c ../SHA256SUMS.txt`を走らせない。GNU `sha256sum -c`は名前をmanifestからの相対ではなく**実行時cwd**から解決するため、本物を改変しても`extracted-check/`内の同名staleコピーが一致して**exit 0（偽PASS）**になる。確実な検証は`scripts/Test-DeliveryManifest.ps1 -ManifestPath <SHA256SUMS.txt> -DeliveryJson <DELIVERY.json>`で、manifestのあるdirから解決するためcwdに左右されない（書式契約・コマンドは`docs/04-package.md`）。

QA記録は合否・版/hash・実施者・日時・証拠・未確認をセットにする。受入項目の正本は`templates/QA.md`の表の行で、行が無い項目は「未確認」の欄自体が生まれないため、記録者の判断で行を落とさない。`scripts/Test-UETemplateScaffold.ps1`が要求行の存在を検査し、1行欠けるとsuiteが落ちる。

`spectator-explore`のrunだけがonline/LAN行を対象にし、他のrecipeのrunは`non-goal`を記録する。`non-goal`は仕様上の非対象に限り、実接続を実施していない項目は`unverified`のまま残す（[少人数online基盤](08-online-foundations.md)）。
