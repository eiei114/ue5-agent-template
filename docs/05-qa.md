# 書き出し・検品

## MRQ→MP4

既存Movie Render Queue plugin、Level Sequence、camera cutsを確認して新projectだけに設定。最初に540×960等の小preview。warm-up値はsceneで調整し、初フレーム黒・shader未完を実画像で検出。ログのmap load成功だけで合格にしない。

推奨開始preset（実装済みassetではない）：vertical=1080×1920、30fps、8秒=240frame。landscape=1920×1080、30fps、10秒=300frame。frame範囲は終端排他とし重複frameを作らない。色空間/露出/warm-up/AA/seed/音の有無を記録。書き出し経路は2つあり、どちらを使ったかを記録する（次節）。経路AはMRQ画像列→既存ffmpegでH264/yuv420p、必要音はAAC/48kHzへ。経路BはMRQの出力設定`H.264 MP4 [8bit]`で直接MP4。UE同梱のMRQ出力設定もencoderとして数える。外部ffmpegの新規導入はしない（無いhostでは経路Bで書くか、既存encoderのあるhostへ回す）。

## 書き出し経路（2つ）

MP4に至る経路は2つある。片方だけを書かない。どちらを使ったかを`templates/QA.md`の`encode_path`へ記録する。既定は経路Aで、経路Bは既定にしない。

| 経路 | 手順 | 元の画像列 | 検査との関係 |
|---|---|---|---|
| A: `mrq-image-sequence+external-ffmpeg` | MRQのimage sequence出力（`.png`/`.exr`）→ 既存`ffmpeg`でH.264/yuv420p | 存在する | 「エンコード前の画像列検査」がそのまま効く（`.exr`列なら`-Extension .exr`を渡す） |
| B: `mrq-native-mp4` | MRQの出力設定`H.264 MP4 [8bit]`（`UMoviePipelineMP4EncoderOutput`）で直接MP4 | **存在しない** | 画像列の検査対象が無い。MP4のffprobeと目視で判定する |

- 経路BのencoderはUEが同梱する`MovieRenderPipelineMP4Encoder`モジュール（`MovieRenderPipeline.uplugin`、`PlatformAllowList`はMac/Win64/Linux）で、recipeの`required_plugins`（`MovieRenderPipeline`）を有効にしたprojectに既に含まれる。追加install・追加課金は不要。
- ただしUE 5.8.4の同梱sourceは`Source/MovieRenderPipelineMP4Encoder/Private/Windows/MoviePipelineMP4Encoder.h:11`で`Experimental.`と明記している。したがって経路Bを既定にしない（画質・音声同期・安定性はこのrepoでは未検証）。
- 経路Bのときは、出力設定の表示名（`H.264 MP4 [8bit]`）を`mrq_output_setting`へ、`source_png_sequence`を「存在しない」と書く。**「元PNG列が無いから unverified」ではなく「経路Bとして記録済み」とする。**片方の経路の前提を他方へ流用しない。
- 経路Aの`ffmpeg`コマンド（`%06d`連番・`-frames:v`）を、経路BのMP4へ流用しない。経路BのMP4は`ffmpeg -n`の再encodeも画像列検査も通らないため、判定はffprobeと目視で行う。**音が対象なら実聴取も必須**で、音声streamの存在やffprobeの音声欄は聴取の代わりにしない（「視覚・ループ・音」節と同じ）。この前提をQAへ書く。
- Epic公式docs（[MRQ概要](https://dev.epicgames.com/documentation/en-us/unreal-engine/movie-render-pipeline-in-unreal-engine)／[高品質フレーム描画ガイド](https://dev.epicgames.com/documentation/en-us/unreal-engine/rendering-high-quality-frames-with-movie-render-queue-in-unreal-engine)、UE 5.8、2026-11-05参照）の出力設定表は`.bmp`/`.jpg`/`.png`/`.exr`/`.wav`のみでMP4の記載が無い。これは**文書の不在**であり、機能の不存在も非推奨という公式見解でもない。

推奨開始preset（実装済みassetではない）：`vertical`（縦動画・ループ）と`landscape`（横動画）。**presetの数値は`templates/CAPTURE-PRESETS.json`だけが持つ**（解像度・fps・秒数・開始番号・桁数・codec/crf）。frame数は`fps × 秒数`で導出する値であり、定義ファイルにも文書にも第2の値として書かない。frame範囲は終端排他とし重複frameを作らない。色空間/露出/warm-up/AA/seed/音の有無を記録。MRQ画像列→既存ffmpegでH264/yuv420p、必要音はAAC/48kHzへ。既存encoderがなければ勝手に導入しない。

presetの数値を手で書き写さない。次の1コマンドが、そのpresetの検査範囲・encodeコマンド・ffprobeコマンド・尺の検査コマンドを定義から生成して表示する（renderもencodeもしない）。

```powershell
.\scripts\Get-UECaptureEncodePlan.ps1 -Preset vertical
```


## エンコード前の画像列検査

MRQの終了通知・exit 0・MP4のframe数は、いずれも元画像列そのものの正しさを証明しない。通知が成功していても、画像列に欠番や余分なframeが混じれば、その後のencodeは静かに別の映像になる。MP4側でframe数を1つ確かめても、「元画像列に余分な1枚がある」ことを排除できない。

そこでencodeの前に、期待範囲と実際の画像列を照合する。`scripts/Measure-UERenderArtifacts.ps1`は読み取り専用のhelperで、対象dirを改名・修復・削除しない。引数の`-StartNumber` / `-EndNumberExclusive` / `-ExpectedWidth` / `-ExpectedHeight`は、`Get-UECaptureEncodePlan.ps1`が出す`FRAMES-CHECK`行からそのまま取る（preset定義の値であり、render範囲を手で書き写さない）。

```powershell
.\scripts\Get-UECaptureEncodePlan.ps1 -Preset vertical
# 出力された FRAMES-CHECK 行を、そのまま実行する。行の形は次のとおり（数値は出力から取る）:
.\scripts\Measure-UERenderArtifacts.ps1 -FramesDirectory '<project>\Out\run_<runid>\frames' `
  -StartNumber <EXPECT の range 開始> `
  -EndNumberExclusive <EXPECT の frame 数 = 終端排他> `
  -ExpectedWidth <EXPECT の幅> `
  -ExpectedHeight <EXPECT の高さ> `
  -RunId '<runid>' `
  -SourceRevision '<template commit>' `
  -ReportPath '<project>\Out\run_<runid>\evidence\frames-check.json'
```

`<...>`を`Get-UECaptureEncodePlan.ps1`の出力で埋める。この文書にpresetの数値を書かないのは、一度書くと定義と文書の二重管理になり、片方だけ直したときに黙って食い違うためである。

- 期待枚数だけでなく、全対象ファイルの番号集合を照合する。先頭・中間・末尾の欠番、範囲外の余分なframe、桁数/拡張子の揺れ、想定外の名前、0 byte、decode不能、解像度不一致を検出する。
- `-Extension`は省略時`.png`。EXR列を検査するときは必ず`-Extension .exr`を渡す。既定のままEXR列を渡すと、EXR frameを想定外の名前、期待するPNG frameを欠番として報告し、正しい列をfailにしてしまう。
- 入力は明示する。`-StartNumber`は0以外も指定できるが、render範囲から書き写す。`-EndNumberExclusive`は終端排他。解像度を省くと解像度判定は`unverified`になり、passにならない。

- 入力は明示する。`-StartNumber`は0以外も指定できるが、render範囲から書き写す。`-EndNumberExclusive`は終端排他。解像度を省くと解像度判定は`unverified`になり、passにならない。**presetを使う場合は`Get-UECaptureEncodePlan.ps1`の`FRAMES-CHECK`行をそのまま使い、数値を文書から転記しない。**
- decodeは既存環境の`ffprobe`を使うだけ。PATHに無い場合は`-DecoderPath`で既存実体を明示する。decoderが無い・失敗・timeoutのときはdecode=`unverified`または`fail`であり、総合passにしない。timeoutは既定10秒で、その場合も成功へ丸めない。
- reportは新規の明示出力先だけに書き、既存fileを上書きしない。文字列上の内部pathに加え、`FramesDirectory`またはreport親pathの既存componentにjunction/symlink等のreparse pointがある場合は、実効境界を安全に照合できないため入力検査・親dir作成より前に拒否する。reportを画像列dirの外側にある通常のdirectoryへ書く。helper自身は入力のhashを計算しない（読み取りしかしない）。「入力が変わっていない」ことは回帰suite `scripts/Test-UERenderArtifacts.ps1` が検証する：suiteが作った18のfixtureディレクトリすべてについて、構築直後の全file名・SHA256をbaselineとして記録し、末尾で再比較して**追加・削除・内容変更をpathで名乗り上げる**。また`reports/`は件数と非空を別途照合し、`Production/`配下の無視される残骸も直接列挙する（`git status --untracked-files=all`は`.gitignore`の`Production/*`を見ないため、これだけでは不十分）。このgate自体が空assertに戻らないよう、「fixtureを壊せばsuiteはそのpathを名指しで落ちる」ことをsuite内の負例groupで固定する。2つのguardは片方だけ外したときに落ちることを別々の負例fixtureで固定する：report親だけをjunctionにしたfixtureと、`FramesDirectory`だけをjunction aliasにしreport親を実体の通常directoryにしたfixtureである。後者は、`FramesDirectory`側のguardを外すとreportがalias経由で検査対象dirに書かれ、そのguardを戻すと書込み前に拒否される（拒否理由が`ReportPath parent`ではなく`FramesDirectory`であることまでassertする）。
- 終了codeはpass=0、fail=1、unverified=2。

## CIのdecoder固定

CIの`render-artifacts` jobは、runner imageに入っている`ffprobe`をそのまま使わない。`scripts/ffprobe-pin.json`に配布元URL・archiveのSHA-256・`ffprobe.exe`のSHA-256・期待するversion行のprefixを記録し、`scripts/Install-PinnedFfprobe.ps1`がその3点を照合してから検査に使う。以前はPATHに`ffprobe`があれば任意版を受け入れ、無い場合はversion指定なしの`choco install ffmpeg`に落ちていたため、同じcommitでもrunner imageやpackage更新でdecode判定が変わり得た。

- 固定した実体はcheckoutの外（`$env:RUNNER_TEMP`、ローカルでは`%TEMP%\ffprobe-pin`）に置き、template・`Production/`・成果物へ同梱しない。CI内のfixture decodeにのみ使う。
- 取得元は`GyanD/codexffmpeg` 8.1.2 essentials build（GPL-3.0-or-later）。archiveのsha256は`db580001…`、`ffprobe.exe`は`b49ccc7c…`、versionは`ffprobe version 8.1.2-`で始まる行。ライセンスはCI内利用に閉じ、repoの配布条件（`LICENSE-NOTICE.md`）とは別物として扱う。
- `scripts/Test-FfprobePin.ps1`が負例を固定する：manifestの項目欠落・archiveの1 byte改変・PATHの手前に別の`ffprobe`がある場合をすべて拒否し、固定版のbytesとversionだけを受け入れる。suiteはcheckout内に何も書かない。
- 判定ロジック（`Measure-UERenderArtifacts.ps1`のdecode/timeout優先順位）と既存assertionは変えていない。固定したのはdecoderの実体だけ。
- 版を上げる場合は`ffprobe-pin.json`の3つの値（archive sha256・binary sha256・version prefix）を同時に更新し、`Test-FfprobePin.ps1`と`Test-UERenderArtifacts.ps1`を通す。片方だけ更新したmanifestはinstallerが拒否する。

判定は次の5つを独立に扱い、1つの欄でまとめない。

| 判定 | 何を見るか | 何を証明しないか |
|---|---|---|
| render通知/exit | MRQの終了通知・exit code | 画像列の完全性 |
| 画像列 | 番号集合・命名・サイズ・decode・解像度。経路Aの必須項目。経路B（direct-MRQ MP4）は対象が存在しないため、`encode_path`=`mrq-native-mp4`と`source_png_sequence`=存在しないの記録を伴う場合だけ`non-goal`と書き、`unverified`のまま放置しない | render成功・映像の見た目 |
| MP4 | 既存ffprobeで幅/高さ/fps/frame数/秒数/codec/音声 | 先頭/中間/末尾の見た目 |
| 目視・全編再生 | 0付近/中間/末尾、全編、loop継ぎ目 | 音の内容 |
| 音 | 実聴取。stream存在は聴取ではない | 映像の見た目 |

画像列がpassでも、render成功・全編目視・音・loop品質は別項目のまま`unverified`とする。逆に通知成功/exit 0の記録があっても、画像列の負例をpassへ読み替えない。

旧runの同数frameが混入していないことは、この検査だけでは判定できない。run専用の新規出力先と所有権照合を前提にする。

## エンコードとMP4の尺検査

上の1コマンドを実行すると、そのpresetの`EXPECT`行（frame数・秒数・解像度・fps・範囲）、`FRAMES-CHECK`・`FFMPEG`・`FFPROBE`・`INSPECT`の各コマンドが、すべて`templates/CAPTURE-PRESETS.json`から導いて表示される。ここに数値例を貼らないのは、貼った瞬間に定義と二重管理になるためである。`frames/`・`Out/final`・`Out/run_<runid>/evidence/`は当該run内のpathに読み替える。

**`-frames:v`は出力frame数の上限であり、尺の検証手段ではない。** 元の画像列がその数より少なければ、ffmpegは少ないままencodeして**exit 0で成功を返す**。したがって「encodeがexit 0だった」「ffprobeが報告した秒数がそれらしかった」のどちらも、presetの尺を満たした証明にならない。`vertical`用のencodeコマンドを`landscape`（10秒尺）にそのまま当てると、短いMP4が成功として得られる。尺の検証は、次の検査器がpreset定義の期待frame数・秒数を実測と照合して行う。

```powershell
.\scripts\Measure-UECaptureEncode.ps1 -Preset landscape -VideoPath '<project>\Out\run_<runid>\final\clean.mp4' -ReportPath '<project>\Out\run_<runid>\evidence\encode-check.json'
```

- 期待値は`templates/CAPTURE-PRESETS.json`のpreset定義から導き、コマンド引数で期待frame数を渡さない。手書きの期待値を渡せる経路を作らないためである。
- 照合するのはvideo stream数（ちょうど1本）、`nb_read_frames`、`duration`、`width`/`height`、`r_frame_rate`。frame数は`fps × 秒数`から導出し、定義側に第2の値として書かせない（書かれていれば`preset_invalid`で落とす）。
- 不一致は`fail`（exit 1）、測れない（ffprobe不在・timeout・stream数不一致で読めない）は`unverified`（exit 2）で、どちらもpassにしない。reportは新規pathにだけ書き、検査対象のMP4を変更しない。
- この検査はMP4の内容だけを見る。元画像列の集合（欠番・範囲外）は`Measure-UERenderArtifacts.ps1`の担当で、両方を別項目として記録する。
- 回帰は`scripts/Test-UECaptureEncode.ps1`。自作fixtureで「300 frame presetを240 frameでencodeするとexit 0のまま`fail`」「正しい300 frameは`pass`」「299 frameは`fail`」「ffprobe不在は`unverified`」「video stream 2本は`fail`」を固定している。

音あり版は同期・尺を合わせ、採用音の権利を確認。音声streamの存在は聴取確認ではない。
公式MRQ： https://dev.epicgames.com/documentation/en-us/unreal-engine/movie-render-pipeline-in-unreal-engine

## 視覚・ループ・音

- エンコード前の画像列検査結果（`evidence/frames-check.json`）を、MP4のffprobe結果と並べて記録する。両方passでも目視の代わりにしない。経路Bでは元PNG列が無いため`frames-check.json`は存在しない。その場合は画像列の欄を`non-goal`とし、`encode_path`/`mrq_output_setting`/`source_png_sequence`の記録で代替する（ffprobe・目視・音の判定は経路Aと同じ水準で行う）。
- ffprobe出力を保存し、実解像度/codec/fps/frame数/秒数/音声を期待値と照合。拡張子や非空サイズだけで合格にしない。

- エンコード前の画像列検査結果（`evidence/frames-check.json`）を、MP4のffprobe結果と並べて記録する。両方passでも目視の代わりにしない。
- ffprobe出力を保存し、実解像度/codec/fps/frame数/秒数/音声を期待値と照合。**期待値の出所は`templates/CAPTURE-PRESETS.json`のpreset定義**（`Measure-UECaptureEncode.ps1`の`evidence/encode-check.json`）であり、実測値を見てから期待値を決めない。拡張子や非空サイズだけで合格にしない。
- 0付近/中間/末尾のフレーム、thumbnailを目視。真っ黒、露出白飛び、被写体切れ、破綻、素材欠落を確認。
- 全編を再生。末尾→先頭を2回連結した再生でも動き/光/カメラ/粒子/音の継ぎ目を確認。数枚目視だけで全編・継ぎ目合格にしない。
- 黒frameが意図外ならwarm-up/camera cut/開始tick/streaming/exposureを調査し再render。黒スクショを「検品済み」としない。
- 実際のゲームと動画の音を聴く。音量、loop click、clip、意図外の無音を確認。遠隔hostで聴けないなら聴取Unverified、owner用previewを渡す。

## Play / 展開版チェック

- 起動map・Pawn・開始姿勢。座位/立位が仕様なら両方。
- mouse視点、移動、zoomの往復、台や壁のcollision、外周の落下/抜け、Rリセット、H help、Esc/終了。未実装の機能は合格にせず仕様上の非対象と区別。
- 最新版で5分以上の連続鑑賞。測定時間・操作/無操作の内訳、hardware、解像度、品質、frame time平均/スパイク/観測方法を記録。
- FPS目安は案件ごとに合意。初期提案は最低30fps（33.3ms）、目標60fps（16.7ms）。これは測定実績でも共通保証でもない。
- 過去Bonfire play8は720p平均13.7〜14.8ms、144.5ms hitchを1回報告。別host/別版へ転用しない。
- Shipping ZIP別展開→起動・操作を再確認。Editor PlayだけではShippingの入力/終了を証明しない。

QA記録は合否・版/hash・実施者・日時・証拠・未確認をセットにする。受入項目の正本は`templates/QA.md`の表の行で、行が無い項目は「未確認」の欄自体が生まれないため、記録者の判断で行を落とさない。`scripts/Test-UETemplateScaffold.ps1`が要求行の存在を検査し、1行欠けるとsuiteが落ちる。

`spectator-explore`のrunだけがonline/LAN行を対象にし、他のrecipeのrunは`non-goal`を記録する。`non-goal`は仕様上の非対象に限り、実接続を実施していない項目は`unverified`のまま残す（[少人数online基盤](08-online-foundations.md)）。
